# Commit Message Standards

This repository follows the **Conventional Commits** specification. Both manual commits and those generated by autonomous agents must adhere to these guidelines to maintain a clean, readable, and automated commit history.

## Format

Each commit message consists of a **header**, an optional **body**, and an optional **footer**. The header has a special format that includes a **type**, an optional **scope**, and a **description**:

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 1. Type
Must be one of the following:

* **feat**: A new feature
* **fix**: A bug fix
* **docs**: Documentation only changes
* **style**: Changes that do not affect the meaning of the code (white-space, formatting, missing semi-colons, etc)
* **refactor**: A code change that neither fixes a bug nor adds a feature
* **perf**: A code change that improves performance
* **test**: Adding missing tests or correcting existing tests
* **chore**: Changes to the build process or auxiliary tools and libraries (e.g., dependency updates)
* **ci**: Changes to CI configuration files and scripts
* **build**: Changes that affect the build system or external dependencies

### 2. Scope (Optional)
A scope may be provided to contextualize the change. It should be a short, lowercase noun describing the section of the codebase (e.g., `ui`, `api`, `auth`, `blog`).

### 3. Description
A short summary of the code changes.
* Use the imperative, present tense: "change" not "changed" nor "changes"
* Do not capitalize the first letter
* No dot (.) at the end

### 4. Body (Optional)
Provide additional contextual information about the change.
* Use the imperative, present tense: "change" not "changed" nor "changes"
* Include motivation for the change or contrast with previous behavior

### 5. Footer (Optional)
Used for referencing issues or noting **BREAKING CHANGES**. A breaking change must contain `BREAKING CHANGE:` at the beginning of the footer or an `!` after the type/scope in the header.

---

## Examples

**Feature without scope:**
```
feat: add dark mode toggle
```

**Feature with scope:**
```
feat(blog): add support for MDX rendering
```

**Bug fix:**
```
fix(ui): resolve overlapping navigation items on mobile
```

**Breaking change (using `!`):**
```
refactor(api)!: remove deprecated v1 endpoints
```

**Breaking change (in footer):**
```
feat: upgrade to Next.js 15

BREAKING CHANGE: Previous routing patterns are no longer supported.
```

**Chore (Dependency update):**
```
chore: update eslint dependencies
```

## Agent Instructions
If an AI agent is committing code, it must:
1. Analyze the `git diff` to understand the full context of the changes.
2. Select the single most appropriate **type**.
3. Keep the description under 72 characters.
4. Provide a body only if the "why" is not immediately obvious from the code changes.

## Modern Best Practices (2026 Standards)

To align with modern software supply chain and collaboration standards, please follow these additional practices:

### 1. Security & Provenance (Signing)
* All commits should ideally be signed using **SSH** or **GPG** keys. This establishes verified code provenance, which is critical when working in environments where both humans and AI agents contribute.
* Use `git commit -S` if your environment is configured for signing.

### 2. Co-authorship for AI/Human Collaboration
When code is heavily pair-programmed with an AI agent or another human, use the GitHub standard `Co-authored-by` trailer in the footer to give proper attribution.
```
Co-authored-by: Antigravity Agent <bot@example.com>
```

### 3. Automated Changelogs & Semantic Versioning
Keep in mind that these commit messages aren't just for reading—they are parsed by CI/CD pipelines (like Semantic Release). 
* `fix:` triggers a **PATCH** release.
* `feat:` triggers a **MINOR** release.
* `BREAKING CHANGE:` triggers a **MAJOR** release.
Avoid using `feat:` or `fix:` if the change shouldn't trigger a new version release (e.g., use `chore:` or `refactor:` instead).

### 4. Issue Tracking
If a commit resolves a known issue or ticket, append it in the footer using standard keywords so issue trackers can auto-close them:
```
Closes #123
Fixes #42
```
